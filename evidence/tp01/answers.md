# TP01 - Answers and Evidence

## Part A - Understand the project and data

**A1. Why should the original CSV, a fitted model and the training source code have different roles in the repository?**

The raw CSV is the original input that must stay unchanged, the source code is the recipe we version in Git, and the trained model is just an output generated from both. Keeping them separate lets us know exactly which data and code produced a given model, so it can be reproduced.

**A2. Why would including `Churn` among the model inputs invalidate the prediction task?**

Because it's what we are trying to predict.

## Part B - Create and inspect the Python environment

**B2 Tasks:**

1. Python constraint in `pyproject.toml`: `requires-python = ">=3.11,<3.13"`. One direct dependency: `numpy~=1.26.0`.
2. Same dependency in `uv.lock`: `name = "numpy"`, `version = "1.26.4"` — the specific version uv resolved within the `~=1.26.0` range.
3. One transitive dependency identified via `uv tree`: `scipy` (pulled in because `scikit-learn` requires it, not declared directly in `pyproject.toml`).
4. Difference between `pyproject.toml`, `uv.lock` and `.venv/`:
   - `pyproject.toml` declares what the project needs, as version ranges (hand-written).
   - `uv.lock` records the exact resolved versions (direct and transitive) with hashes, so the resolution is reproducible across machines (generated by uv).
   - `.venv/` is the materialized environment on this machine, built from the lock file. It's disposable: delete it and `uv sync --locked` rebuilds it identically; it is never committed to Git.

## Part C - Inspect and fingerprint the Telco dataset

**C3. Interpret the result:**

1. **Why is churn prediction a classification task?** `Churn` has two discrete values (Yes/No), not a continuous number, so the model predicts a category, not a quantity.
2. **What does the class balance suggest about using accuracy alone later?** About 73% of customers don't churn. A model that always predicts "No" would already score ~73% accuracy without learning anything. Accuracy alone would hide poor performance on the minority ("Yes") class, so recall/precision/F1 are needed too.
3. **Why can `TotalCharges` be read as an object/string column even though it represents a numeric quantity?** Some rows contain whitespace-only values instead of numbers, so pandas can't infer a numeric dtype for the whole column and falls back to text (object).
4. **Why may `isna()` alone fail to detect a whitespace-only value?** A string like `" "` is not `NaN`, it's a valid non-null string, so `isna()` returns `False` for it even though it holds no real value. It must be stripped and checked for emptiness explicitly.
5. **Which evidence would tell a teammate that they inspected the same source file?** A matching SHA-256 hash (recorded in `telco.source.json`), not just a matching filename — the hash proves identical bytes.

## Remaining reproducibility limitations

- Only package selection and source data identity are verified here; no model has been trained yet.
- Hardware/platform differences (e.g. arm64 vs x86_64) are not captured by the lock file and can still break an environment even when `uv sync --locked` succeeds.
- The hash check confirms identical bytes, not that the data is free of labeling errors or leakage.
